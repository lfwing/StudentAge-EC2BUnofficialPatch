RoleAvailability：角色社交与空间可见性
适用于UP 1.0.23.1；需启用[机制]控制角色可见性。

一、安装与开关

启用 UP cfg 的 [机制]「控制角色可见性」。
将 RoleAvailabilityCfg.json 放到启用的 Mod 中，推荐路径：
Mod根目录/EC2BUnofficialPatch/RoleAvailabilityCfg.json
也支持 Mod 根目录或其他多层容器。模板目录只供复制参考，不直接参与角色登记。
使用 UTF-8、标准 JSON：不要写注释、中文引号或末尾多余逗号。
角色、空间内容和评论仍须通过原版 PersonCfg、KZoneContentCfg、KZoneCommentCfg 等注册。
本功能不创建角色、不发布内容、不自动关注角色，也不改变关系门槛。

二、完整配置示例

下面的 ID 是示例，请替换为你的 Mod 中已登记的 ID。
{
  "roles": [
    {
      "personId": 114514,
      "cond": [[1,1,1,100]],
      "takeExam": false,
      "hiddenkzone": true
    },
    {
      "personId": 102,
      "cond": [],
      "takeExam": true,
      "hiddenkzone": false
    }
  ]
}

第一项：主角智力达到100后，角色114514才通过默认社交可见性检查；不参加考试；
该角色发布的空间内容仍正常发布，但默认不显示。cond 与 hiddenkzone 相互独立。
第二项：角色102不额外限制社交显示、允许参加考试，空间按原版规则显示。
允许考试还要求实际考试数据齐全，不能替缺少考试数据的自定义角色补齐考试功能。

三、字段

roles：角色条目数组；没有需要控制的角色时使用 {"roles":[]}。
personId：必填，正整数，角色 PersonCfg ID。同一角色不要在文件内或不同 Mod 中重复登记。
cond：原版前提二维数组，多条按原版 AND 组合；省略、null 或 [] 均不增加前提限制。
      [[1,1,1,100]] 是主角智力至少100；其他前提按原版或已启用的 UP 前提格式填写。
      cond 只决定默认社交可见性，并参与原有考试准入检查，不负责发布空间内容。
takeExam：必填布尔值。false 排除考试资格；true 保留原有考试准入检查。
          true 要求 Person、运行时 Role、当前学段 PersonGrow.examRank 和对应 Classmate 排名数据完整。
hiddenkzone：可选布尔值，默认 false。true 隐藏该角色署名的空间内容；false 不额外隐藏。
             范围包括动态、日志、附属图片、评论、留言及留言回复、点赞。
             按作者计算，包括该角色在别人空间留下的内容。
             匿名点赞数量没有作者ID，不能单独指定其属于某个角色。

未登记角色不增加默认限制。重复 personId 的冲突条目全部禁用并记录日志；
冲突角色的默认社交/考试资格按不可用处理，空间不采用冲突配置。
不合法或缺少必填字段的条目会忽略并记录日志，请先排查日志中的配置错误。

四、社交显示/隐藏效果

[22,999,2,114514]   在社交列表显示角色114514关注对象。
[22,999,3,114514]   在社交列表隐藏角色114514。

效果写进原版支持的 effect 字段，例如：
"effect": [[22,999,2,114514]]
多条效果在外层数组继续添加，不要将此效果写进 cond。

优先级：该角色最近一次显示/隐藏效果 > cond；未执行过效果时才使用 cond。
显示指令可在 cond 尚未满足时显示已关注角色；不会自动关注，
也不会把原版社交候选范围以外的角色强行加入列表。
隐藏后即使 cond 满足仍会隐藏；重新执行显示效果才解除本次隐藏。
社交指令不改变考试资格，不改变空间可见性。

示例：剧情结识并关注角色114514后执行 [22,999,2,114514]；
暂时离开时执行 [22,999,3,114514]；回归时再次执行显示指令。
指令不要求角色已在本 JSON 登记，但必须有有效角色数据。

五、空间单条与角色批量效果

[23,3,1,301]       显示已经发出的 ID=301 动态或日志及其附属图片。
[23,3,-1,301]      隐藏已经发出的 ID=301 动态或日志及其附属图片。
[23,3,2,9001]      显示已经发出的 ID=9001 评论。
[23,3,-2,9001]     隐藏已经发出的 ID=9001 评论。
[23,3,999,114514]  显示角色114514署名的、执行时已发出的空间内容。
[23,3,-999,114514] 隐藏角色114514署名的、执行时已发出的空间内容。

±1 的末项是 KZoneContentCfg ID；±2 的末项是 KZoneCommentCfg ID。
不是角色ID；±2 也不是留言板ID。留言板、留言回复和点赞通过 ±999 批量控制。
批量范围包含该角色在别人动态下的评论、在别人留言板的留言/回复，以及点赞。
动态下其他作者的评论不会因批量显示某作者而自动显示；图片跟随所属动态/日志。
隐藏父动态时，其评论和图片也不可见；隐藏父评论或父留言时，回复一并暂时不可见，
但回复自己的显示状态保留，父项恢复后再按其自身状态判断。

效果只修改显示状态，不调用发布流程，不补发缺失内容，不重置时间或重复发放发布奖励。
内容尚未发出时执行单条指令不会预约未来显示；请在原版发布效果之后执行。
批量指令只处理“当前已发布内容”，不是对该角色未来内容设置永久开关。
之后新发出的内容继续按 hiddenkzone 决定默认可见性。
单条与批量指令对本次实际处理的内容以最近一次结果为准，高于 hiddenkzone；
批量只修改当前需要改变状态的项，不会将已符合目标状态的项额外冻结为覆盖。
不会因 F9 或之后修改 hiddenkzone 而清除已保存的指令结果。
显示仍受原版页面、所属空间、内容类型等筛选约束，不会强行加入不属于该页面的内容。

六、组合示例：先发布，后揭示

1. 配置角色114514的 hiddenkzone=true。
2. 使用原版流程发布该角色动态；记录、评论生成及时间正常推进，玩家暂时看不到。
3. 揭示时执行 [23,3,1,301]，仅显示指定动态；
   或 [23,3,999,114514]，显示该作者当前已发布的动态、日志、评论、留言和点赞。
4. 显示后的内容按原发布时间排序，不会移动到最新位置；相同时间戳按内容ID稳定排序。
5. 只隐藏评论时执行 [23,3,-2,9001]，不必隐藏整条动态。
301/9001只是格式示例，实际替换为已发布的对应ID，且作者应与场景一致。

已经完成原版发布后，效果字段可写：
"effect": [[22,999,2,114514],[23,3,999,114514]]
含义：显示该关注对象，并揭示其已发布的空间内容；两套可见性分别修改。

七、存读档、热重载和排查

指令结果随当前存档保存；读入其他存档或开始新游戏不会继承本档状态。
切换触发指令的特质不会撤销已经执行的显示/隐藏决定。
修改 JSON 后可用 F9 读取；相关列表会刷新，已保存的覆盖决定保留。
关闭「控制角色可见性」并重启后不再过滤；重新启用仍使用本档中的覆盖决定。
原版 CFG 的注册限制仍遵循原版流程，F9不能替代所有情况下的重启。

角色仍看不到：先确认角色已创建并关注、原版列表本来包含它，再检查 cond、
最近一次社交隐藏指令和日志。显示指令不会建立关注关系。
动态仍看不到：先确认已真正发布、ID类别正确、页面允许该内容，再检查 hiddenkzone、
最近一次单条/批量指令，以及父项是否隐藏。
留言回复仍看不到：同时检查留言作者及父留言可见性。
改 hiddenkzone 却未改变旧内容：可能已有指令覆盖，请再执行对应显示/隐藏指令。
效果数组为原版 float 通道，示例ID均可精确表示；自定义ID仍须遵守原版数字精度限制。
